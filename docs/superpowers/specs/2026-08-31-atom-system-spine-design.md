# Atom 系统主干设计

## 1. 设计目的

- **目标**：把 Atom 后续开发的共同产品合同写成可跨 Session 读取、可继续拆计划、可由代码与真实路径验证的 Superpowers 设计规格。
- **迁移对象**：GitHub 30 个 Issue、42 个已合并 PR、293 条 Issue/PR 对话，以及仍能约束当前产品的 OpenSpec、架构文档、代码和测试事实。
- **当前范围**：只处理 Atom；其他仓库不迁移，也不分散本阶段精力。
- **采用决定**：Superpowers 6.3.0 是既定开发方法，不再评估是否采用；遇到困难进入其调试、TDD、审查与验证流程。
- **非目标**：不修改 Superpowers，不为 Atom 发明第二套工作流、状态机、Issue 数据库或规格语法。

## 2. 定论与证据

### 2.1 权威关系

- **产品合同**：用户最新且仍有效的定论定义“应当怎样”；新旧冲突时采用新定论，并保留被替代内容的来源关系。
- **实现事实**：当前 `main` 的代码与已合并 PR 说明“现在实现了什么”，不能反向覆盖产品合同。
- **完成证据**：与当前版本绑定的测试、真实 CLI/Web 路径、事务与恢复结果说明“当前是否成立”。
- **历史追溯**：Issue 状态、评论结论、PR 描述、OpenSpec 勾选和旧能力图只说明演进过程，均不能单独证明完成。
- **矛盾处理**：发现“已关闭/已验收”与当前代码或真实路径不一致时，保留历史说法，按当前合同重新形成 RED 证据并作为开发输入。

### 2.2 迁移结构

```text
完整原始材料（外部只读备份，可恢复）
        ↓ 语义去重、冲突裁定、关系保全
Superpowers 设计规格（本目录，定义应然）
        ↓ writing-plans
实施计划（任务、文件、测试、执行顺序）
        ↓ TDD / systematic-debugging / review
代码与当前版本证据（定义实然与完成）
```

- **原始层**：完整材料留在仓库外的迁移备份中；不把数百条评论平铺进每次 Agent 上下文。
- **设计层**：本文件保存全局不变量和跨域关系，五份伴随规格保存各自内聚合同。
- **执行层**：后续仅由官方 `writing-plans` 生成计划；设计规格本身不伪装成任务状态。
- **证据层**：测试和运行证据必须绑定接受验证时的代码版本；旧证据只用于定位回归与复用测试意图。

## 3. 系统边界

### 3.1 组件所有权

- **世界内核**：拥有 Atom 身份、内容、层级、关系、Program 源码与 Agent 注册事实。
- **运行脊柱**：拥有交互生命周期、世界修订、事务提交、Program 运行结果与中央回执。
- **投影体验**：投影系统拥有可重建的 Graph/Spatial 读模型；空间体验拥有相机、焦点、选择、展开和布局覆盖等视图事实。
- **入口适配**：CLI、HTTP、Web 只翻译意图并呈现回执，不建立第二套业务语义或权限语义。
- **运行保障**：拥有备份、恢复、健康、诊断与当前版本验收；开发治理只维护规格—计划—实现—证据的可追溯关系。

### 3.2 全局不变量

- **唯一事实源**：`atom.json` 经 world repository port 提交，是唯一业务事实源；Graph、Spatial、索引、缓存和浏览器回显均可重建。
- **统一交互链**：所有入口进入同一条“意图 → 查询/Program → 原子提交 → 投影 → 回执”脊柱。
- **数据视图分离**：世界编辑只改变世界事实；没有显式视图意图时，不得改动相机、焦点、选择、展开或视图模式。
- **有序精确提交**：每个操作至多形成一次明确提交；旧快照、重试和异步投影不得覆盖更高修订。
- **真实路径验收**：关键用户能力必须经过其实际入口、提交、回显和结果链；源码匹配、模型值变化或局部单测不能代替用户结果。

### 3.3 关键用户链

- **Agent 使用**：给出明确 Agent 身份 → CLI 解析上下文 → 同路径权限裁定 → 查询或 Transform → 稳定回执。
- **Program 转移**：事实与关系定位 → 独立 Program 判定/执行 → 同一事务提交 → 关联投影更新。
- **Web 编辑**：空间输入 → 数据意图 → 中央提交 → 权威投影回显，同时保持视图连续。
- **Web 导航**：空间输入 → 视图意图 → 权威路径加载 → 场景变化，不写业务事实。
- **恢复闭环**：提交与中央记录 → 私密备份 → 故障定位 → 恢复 → 按当前合同复验。

## 4. 规格拆分

### 4.1 拆分规则

- **拆分单位**：独立用户结果、明确所有者边界、专属不变量、可独立计划与验收同时成立时，形成一份规格。
- **不得采用**：不按单个 Issue、单个 PR、单个文件或一次报错机械拆规格。
- **交叉能力**：每项历史需求只指定一个主要规格；其他规格通过依赖和验收场景引用，不重复定义合同。
- **小型缺陷**：若不改变架构边界，只进入所属规格的错误场景和回归验收，不另造规格。
- **超大变化**：若一份规格不能由一个内聚计划实施，则在用户审阅后继续按同一规则拆分，而不是拍平任务颗粒度。

### 4.2 伴随规格

- **世界与 Program**：`2026-08-31-atom-world-program-design.md`，定义事实、Transform、Program、support、Shortcut 与备份域语义。
- **Agent 与授权**：`2026-08-31-atom-agent-authorization-design.md`，定义注册格式、标签、作用域、窗口和迁移边界。
- **运行与恢复**：`2026-08-31-atom-runtime-projection-recovery-design.md`，定义修订、提交、投影、局部性、就绪和恢复。
- **Web 与空间**：`2026-08-31-atom-web-spatial-design.md`，定义加载、编辑、导航、复合关系与移动端真实体验。
- **验收与运维**：`2026-08-31-atom-acceptance-operations-design.md`，定义官方 Superpowers 执行链、跨 Session 衔接和完成证据。

## 6. 当前缺口与实施边界

### 6.1 已知缺口

- **Agent 归属**：Agent 不是 Key 标签；最新合同要求由 `thing@program` 的 Program 正文承载恰好一个合法字面量 `agent({...})`，并由 Program 完成 Agent 派发。当前 CLI 帮助与多项测试仍保留 `@agent` Key 语义，不能宣称完成。
- **零 Agent 创世**：#14 尚未设计为可实施闭环；当前系统不得声称无既有 Agent 时也能自助创世。
- **证据重绑定**：若干关闭 Issue 和未勾完 OpenSpec 与后续 PR 互相矛盾；需要按当前 `main` 重建聚焦证据，而非批量继承 Accepted。
- **真实路径门禁**：旧能力图指出能力到完整用户路径的强制映射不足；其状态已过期，但这一结构性风险仍需当前版本证据消除。

### 6.2 实施约束

- **保持演进式单体**：先修复触及范围内的边界，不启动全仓重写或服务化。
- **保护私密事实**：不得把 `atom.json`、业务正文、密钥、私有备份或本地绝对路径提交到公开仓库。
- **保持可回退**：代码实施前使用隔离 worktree；每个计划明确 Git 回退点、数据备份和恢复验证。
- **禁止状态复制**：不把 GitHub Project、Issue 标签或 OpenSpec checkbox 翻译成新状态表；只翻译合同、因果关系、失败案例和验收意图。
- **完成定义**：只有当前版本的必要测试与真实用户链通过，且审查未发现合同偏离，才能对相应计划声称完成。

## 7. 设计验收

- **结构完整**：30 个 Issue、42 个 PR 具有唯一主要归属，293 条对话的有效定论被语义吸收，原文可从外部备份恢复。
- **合同一致**：五份伴随规格共同遵守唯一事实源、统一交互链、数据/视图分离、有序提交和真实路径验收。
- **冲突可见**：关闭、合入、勾选与当前事实冲突时，没有被静默抹平或误报为完成。
- **官方衔接**：用户审阅本规格包后，下一步只能进入 Superpowers 官方 `writing-plans`，再按计划执行 TDD、调试、审查与完成前验证。
- **范围克制**：本规格包不改产品代码、不恢复 GitHub 状态机、不继续 OpenSpec 工作流，也不处理其他软件。
