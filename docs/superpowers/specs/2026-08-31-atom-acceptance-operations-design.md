# Atom 验收与开发运作设计

## 1. 责任边界

- **负责**：定义 Atom 如何严格使用 Superpowers 6.3.0、如何跨 Session 衔接、如何选择验证范围、如何审查与声称完成。
- **依据**：采用 Superpowers 已确定；“适应代替验证”表示遇到困难解决困难，不表示删除产品验证。
- **不负责**：不建立 Issue 管理器、自定义状态机、第二份需求库或 Superpowers 分支。
- **主要来源**：Issue #1、#3、#6、#10 及全部 Issue/PR 中反复出现的假完成、重开和真实路径教训。

## 2. Superpowers 官方执行链

### 2.1 工作分类

- **入口选择**：每次实质开发先由 `using-superpowers` 选择适用技能，不因全局安装而自动运行所有技能。
- **Spike**：只回答可行性，先说明探查问题和低成本方法，结果不作为可保留实现。
- **Bounded**：已有明确代码流的小改动，在聊天中给出短设计并取得批准后，直接进入 TDD 实施，不创建规格文件。
- **Architectural**：新增子系统、重划边界或改变依赖接口，执行 brainstorming → 书面规格 → 用户审阅 → writing-plans。
- **只升不降**：发现隐藏复杂度时升级路径；不得为绕过设计或审批把复杂任务伪装成小改动。

### 2.2 重度受控默认

- **设计门**：架构和跨层变化先用官方 brainstorming；批准前不写实现代码。
- **计划门**：书面规格经用户审阅后，用官方 writing-plans 写到文件级、测试级和命令级。
- **隔离门**：开始多步实现前使用官方 using-git-worktrees，在干净、可回退的 worktree 工作。
- **实现门**：功能与修复执行 test-driven-development；遇到异常先执行 systematic-debugging，不凭猜测堆补丁。
- **收口门**：完成前依次取得请求审查、处理审查意见、运行 verification-before-completion，并按 finishing-a-development-branch 选择集成方式。

### 2.3 技能调用颗粒度

- **按任务调用**：Superpowers 的单位是有明确结果和范围的开发任务，不是把每个历史 Issue 机械变成一次全流程。
- **规格聚合**：共同用户结果、所有者和不变量相同的历史问题进入同一设计；单点回归作为该设计的错误/验收场景。
- **计划拆步**：writing-plans 把一个已批准规格拆成可验证的小任务；拆分发生在计划内部，不制造外部平行规格体系。
- **调试嵌入**：计划执行中出现失败时，对该失败调用 systematic-debugging，然后回到原计划验收断点。

## 3. 跨 Session 与协作

### 3.1 持久交接物

- **设计规格**：保存产品目标、边界、不变量、错误和验收，解释“为什么、应当怎样”。
- **实施计划**：保存任务顺序、精确文件、测试、命令和依赖，解释“下一步怎样做”。
- **Git 状态**：commit/worktree/diff 保存实际修改；测试输出和当前代码共同说明“做到哪里”。
- **历史备份**：完整 GitHub/OpenSpec 原文在仓库外只读保全，只在出现歧义或追溯需求时读取。
- **聊天非权威**：聊天正文、自动压缩摘要、Agent 记忆和口头状态只用于当轮协作；任何在压缩后仍会影响实现、优先级、验收或恢复的语义，必须在当轮结束前进入相关规格或实施计划。
- **证据断点**：当前计划用勾选项记录已取得证据的任务，并在“恢复断点”中绑定代码 revision、验证命令、真实入口结果、未完成项和下一动作；不得用“前文已说明”代替。

### 3.2 Session 启动

- **读取顺序**：先从 `docs/superpowers/README.md` 找到当前规格和计划，再读相关规格与计划的恢复断点，随后检查 Git/worktree、近期提交与当前测试；不从旧聊天或自动压缩摘要猜状态。
- **范围恢复**：只加载当前任务所需伴随规格和来源，系统主干用于校验跨域不变量。
- **事实校正**：计划勾选、Agent 自报或旧测试与代码冲突时，以当前代码和重新取得的证据校正，不静默推进。
- **继续执行**：从首个未取得当前证据的计划任务继续；不重做已有可靠证据，也不因 Session 切换重开需求研讨。

### 3.3 Session 消息的常态翻译与持久化

- **逐条翻译**：每条会影响后续开发的用户消息到达后，先判断它属于产品定论、执行状态、实现事实还是临时反馈，再分别写入相关规格、实施计划或 Git/测试证据；不把聊天本身当作存储层。
- **定论入规格**：目标、术语、行为、边界、优先级和验收变化进入相应 Superpowers 规格；与旧定论冲突时明确替代关系，不把两套要求并列运行。
- **状态入计划**：已完成步骤、失败根因、当前阻塞、验证结果和下一动作进入相应实施计划；计划只绑定可核对证据，不复制整段聊天。
- **即时收件**：不打断当前主线的 Bug 或需求立即进入所属规格的待设计/待修场景，并保持用户给定的优先级；进入实现前再走对应 brainstorming 与计划，不靠记忆排队。
- **当轮落盘**：出现上述有效信息时在当前工作回合内更新对应文件，不等待 Session 结束、上下文接近上限或人工提醒。
- **压缩无关**：常态持久化不是为换 Session 或防压缩临时增加的步骤；即使当前 Session 永不切换，也必须执行同一翻译链。
- **中断可恢复**：断电、断网、应用故障或上下文压缩后，新 Agent 仅凭仓库和当前 Atom Help，能够定位当前计划、判断已完成与未完成边界并执行第一条未完成步骤。
- **无证据不继承**：只存在于聊天而未进入规格/计划的说法不得作为产品定论或完成证据；恢复时将其视为缺失信息，而不是凭相似代码猜测。
- **索引非账本**：`docs/superpowers/README.md` 只提供权威文件的导航和恢复顺序，不复制需求、任务状态或完成结论，避免形成第二套状态系统。

### 3.4 多 Agent 边界

- **可并行条件**：任务没有共享可变状态、没有顺序依赖，并且每项拥有明确文件边界和验收时，才并行派发。
- **主控责任**：执行 Agent 的自报不是最终结论；主控回到规格、diff 和证据独立裁定。
- **冲突避免**：共享核心文件或同一事务语义由一个实现任务负责，其他 Agent 可做独立调查或审查。
- **人工角色**：用户负责目标反馈和推进；Agent 负责已授权的分析、编码、测试与证据生产，不把技术判断拆成零散确认题。

### 3.5 当前 Session 巡守

- **心跳频率**：当前 Atom 开发 Session 每1小时执行一次增量巡守；每轮先从当前需求总账与`docs/superpowers/README.md`恢复，不把heartbeat prompt或聊天历史当作产品状态。无实质变化保持安静，不重复全量审查。
- **继续条件**：相关规格或计划仍有未解决 Bug、未完成需求或未取得证据的任务时，Agent继续执行首个能够从现有定论可靠推出的步骤，尤其优先处理用户亲口提出且尚未关闭的事项。
- **裁定依据**：用户最新且仍有效的定义和产品定位最高；当前 Superpowers 规格、实现事实、可复现故障与测试证据用于补足裁定。Atom CLI `submit`只表示 Agent 交互反馈线索，不构成需求、优先级、根因或完成权威。
- **不确定请示**：只有缺少产品取舍、外部事实或授权，导致多个方案无法按既有定论裁定时，才形成短简报，列出已知事实、冲突点、影响和需要用户决定的一项问题；等待期间仍可继续不依赖该决定的安全工作。
- **确定即推进**：能由既有定论、代码事实和验证合同得出结论的事项，不因心跳切段反复请示；按 Superpowers 对应技能持续调试、TDD、验证、持久化和提交，直至实际完成或出现真实阻塞。
- **增量约束**：每轮先检查 Git、当前计划和自上轮以来的变化；无变化时不做批量审查、全量测试、重复部署或重新调查，避免周期任务放大 token 消耗。
- **每轮落盘**：新收件、根因、设计裁定、实现进度、验证结果和下一断点在当轮进入相应规格/计划/Git；心跳结束前不得只把进度留在输出消息中。

## 4. 证据与完成

### 4.1 证据层级

- **合同测试**：证明解析、错误码、接口与局部不变量。
- **系统测试**：证明中央事务、Program、权限、投影和恢复等跨组件关系。
- **真实入口**：证明公共 CLI、HTTP 服务或真实浏览器完成完整用户结果。
- **故障证据**：证明提交前/后失败、冷启动、回退和缓存损坏不会破坏事实。
- **版本绑定**：每份完成证据记录代码 revision、测试命令、结果和必要环境；旧数量不自动继承。

### 4.2 验证范围

- **每个计划任务**：先运行能制造 RED 的最小测试，再实现到 GREEN，并运行直接邻接回归。
- **跨层变化**：运行受影响的完整真实用户链，不以大量低层测试替代。
- **完整套件**：只在仓库强制 CI、发布候选、跨层高风险或影响面无法可靠收窄时运行。
- **避免无度消耗**：任何扫描、全量测试、重复审查或部署都要关闭一个明确门禁或不确定性；相同版本的既有可靠证据可复用。
- **不削弱质量**：额度和时间不允许把未取得证据的功能写成完成；资源不足时保留准确缺口和恢复点。

### 4.3 完成判据

- **实现一致**：diff 与批准规格一致，没有顺手扩张或遗留双实现。
- **当前证据**：必要的 RED→GREEN、邻接回归、真实入口和故障场景在当前 revision 通过。
- **独立审查**：审查覆盖需求、架构、错误边界、测试质量和回退；意见经技术核验后处理。
- **恢复可行**：代码和数据的回退点明确，涉及迁移时已演练恢复或具备等价可执行证据。
- **准确陈述**：只声明实际完成的范围；Closed Issue、merged PR、checkbox、测试数量或部署成功均不能单独满足本判据。

## 5. GitHub 与 OpenSpec 退役边界

### 5.1 GitHub

- **保留用途**：远端 Git、PR 和 Issue 可继续作为历史、代码托管或必要协作载体，但不再担任 Atom 的需求/完成状态权威。
- **不做镜像**：不把本规格再逐条同步回 GitHub Project，也不要求每次 Superpowers 调用对应一个 Issue。
- **必要发布**：未来是否 push/PR 按具体实施计划和用户授权决定；本地 Git commit 与备份足以先形成恢复点。
- **历史查询**：需要追溯时从只读迁移备份读取完整正文/评论，再用最新规格和当前事实裁定。

### 5.2 OpenSpec

- **停止新建**：Atom 后续普通开发不再创建、继续、同步或归档 OpenSpec change。
- **历史保全**：既有 proposal/design/spec/tasks/verification 作为来源证据保留，不删除、不覆盖。
- **语义吸收**：仍有效合同进入本规格包；未勾项和冲突用于发现差距，不直接转换为 Superpowers 任务状态。
- **发现隔离**：后续实施计划应明确如何让旧 OpenSpec 退出 Agent 的活跃控制发现路径，同时保持可恢复历史。

### 5.3 Superpowers

- **唯一含义**：采用官方 6.3.0 技能定义和默认文件约定；本规格包只是官方 brainstorming 的产物。
- **官方只读**：已安装插件内的 Skill、引用、模板、规则、定义和其他框架要素一律不编辑、不覆盖、不影子复制、不包装改义；项目规格和计划只提供 Atom 输入。
- **不扩展框架**：不增加 Atom 专属状态名、审批级别、Issue 同步器或自动技能全开规则。
- **冲突处理**：项目文件若与当前官方规则冲突，先停止冲突动作并按当前官方规则修正项目文件，不修改官方规则来迁就项目。
- **版本处理**：升级 Superpowers 时先读取新版官方技能差异，再按新版调整执行方式；产品合同仍由 Atom 规格保存。
- **安装与调用**：全局安装不等于调用，也不消耗任务上下文；只有当前任务匹配并实际读取/执行技能时才产生工作量。

## 6. 本次迁移验收

- **恢复性**：迁移前 Git 全引用 bundle、GitHub 规范化导出、OpenSpec/架构源快照和 SHA-256 清单均已在仓库外校验。
- **结构性**：系统主干给出权威关系、组件、不变量、关键旅程和完整 Issue/PR 主归属；五份规格按真实边界展开。
- **完整性**：原始对话不被删减，活跃规格又不平铺 293 条评论；新旧冲突、关闭不等于完成和缺失 Project 字段均明示。
- **安全性**：规格不包含 `atom.json`、业务正文、凭据、私密备份或本地绝对路径。
- **下一门**：用户审阅并批准书面规格后，才调用官方 `writing-plans`；在此之前不改 Atom 产品代码。
