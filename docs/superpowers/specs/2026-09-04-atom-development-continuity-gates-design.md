# Atom 开发连续性与有效交付门禁设计

## 1. 目标与边界

- **目标**：让现有Superpowers开发链在需求收件、计划定稿、任务启动、验证升级和提交收尾五个节点失效封闭，防止首要目标被等待、重复验证、审查或临时事项持续挤走。
- **依据**：2026-09-03 00:00—09:00本机会话记录显示，期间形成多项提交和两次部署，但用户首要推支直到08:45才成为可用交付；同时出现至少4次完整测试启动、19次Agent等待超时及进展账本滞后。
- **不改框架**：不修改、包装、覆盖或影子复制官方Superpowers插件；不增加常驻进程、第二套账本、逐命令执行票或新的开发调度器。
- **项目内落点**：规则只进入Atom的`AGENTS.md`、本规格、当前实施计划、既有开发控制测试和一个小型只读校验入口。
- **兜底关系**：每小时巡守只负责发现异常中断和账本漂移；日常正确性必须由五个事前／事中门禁保证。

## 2. 权威信息与分级

### 2.1 单一所有权

- **需求总账**：唯一拥有当前事项、状态、优先顺序和延后关系。
- **产品规格**：唯一拥有获批目标、行为、边界和验收语义。
- **当前计划**：唯一拥有当前开发事项的任务顺序、实质进展、验证证据和下一动作。
- **Git与验证**：提供实现事实和证据，不另立需求或状态系统。
- **README**：只导航上述文件，不复制状态。

### 2.2 四项计划字段

每个进入实现的事项必须在当前计划中声明：

- **重要度**：`I3`核心合同／数据／安全，`I2`主功能，`I1`体验质量，`I0`可选优化。
- **紧急度**：`U3`当前使用阻断，`U2`当前里程碑阻断，`U1`已排期，`U0`待办。
- **困难度**：`D0`机械修改，`D1`有界改动，`D2`跨模块，`D3`架构或高不确定性。
- **目标交付层级**：`E1`规格确定，`E2`实现与测试完成，`E3`部署且公共入口回读，`E4`真实使用确认。

排序先服从用户明确优先级，再按必要依赖、紧急度和重要度裁定。困难度只决定拆分方式，不能使简单事项越过更重要或更紧急的事项。用户要求“着急使用”时，目标交付层级默认不得低于`E3`。

这些字段是当前Superpowers计划内的项目元数据，不是新的框架状态机或审批层级；它们细化本项目既有计划输入，不改变官方技能定义。

## 3. 五个现有阶段门禁

### 3.1 需求收件门

- 影响后续开发的用户消息到达后，先按现行接受运作规格判断其属于定论、状态、事实或临时反馈。
- 新需求、缺陷、优先级、边界或验收变化必须在当前回合写入总账或相应规格；不等待用户询问进展。
- 新收件不得自动打断当前首要目标；只有用户明确改序或它被证明是首要目标的必要依赖时才进入当前计划。
- 该门主要是语义门禁；脚本不得解析Codex私有会话JSONL或把聊天变成第二份需求库。

### 3.2 计划定稿门

- 当前计划缺少`I/U/D/E`、唯一目标、最短交付链、必要依赖或验收终态时，不得进入实现。
- 计划必须把真实用户链放在验证顺序中，不能只列单元测试或全量测试。
- 跨模块、高不确定性事项通过Superpowers既有brainstorming和writing-plans处理；本门禁不增加新的审批层级。

### 3.3 任务启动门

- 每个工作单元只能执行当前计划首个尚未取得证据的步骤，或该步骤已明示的必要依赖。
- Agent审查、工具调查和等待必须绑定当前步骤的具体不确定性；不能因“顺便”“等待期间”开启无关修复。
- Agent等待不得成为独立工作单元，也不得连续原样重试；单次主动等待默认不超过60秒。存在本地可推进步骤时继续本地工作。确无可推进步骤时记录真实阻塞，而不是把等待描述为进展。
- 根因确认、RED、GREEN、阶段提交、部署回读或真实阻塞一旦形成，立即更新当前计划；普通命令、无状态轮询和重复解释不写入计划，避免日志噪声。
- 门禁失败后的下一动作是补齐计划或回到首个合法步骤；禁止原样重试被拒动作。

### 3.4 验证升级门

验证顺序固定为：

```text
最小受影响链 → 真实关键旅程 → 系统门禁 → 候选冻结 → 最终全量一次
```

- 当前层未通过，不得进入下一层。
- 真实关键旅程尚未完成、候选代码仍在变化或已知审查阻断尚未关闭时，禁止启动最终全量。
- 同一候选revision的可靠验证证据复用；不得因状态汇报、巡守或无代码变化重复全量。若首次全量没有形成有效证据是因为明确的基础设施／执行器失败，可记录原因后重跑；真实测试失败必须先回到定向调试，不能原样重跑全量碰运气。
- 最终全量后若产品代码改变，候选解冻并从最小受影响链重新验证；只有所有定向缺口关闭后才能再次形成新的最终候选。
- 质量、安全、数据守恒、迁移和回滚所需证据不得以节省Token或时间为由删除；本门禁控制顺序和重复，不降低完成标准。
- 该顺序只约束计划判定为必要的验证层级；有界低风险改动若按现有影响分析不要求系统或全量，可以在其声明的最高必要层收口。凡需要全量时，全量必须位于最终候选末端且原则上只运行一次。

### 3.5 提交收尾门

- 产品代码或测试进入提交时，当前计划必须在同一工作单元更新：已完成步骤、当前revision对应证据、剩余风险和下一动作。
- 提交前沿用既有`detect_changes()`、差异检查、Ponytail从属最小化检查和`verification-before-completion`，不得新增重复审查轮次。
- 用户要求可用交付且目标为`E3/E4`时，代码提交不能关闭事项；必须继续到部署、公共入口回读及适用的真实使用证据。
- 推送仍遵守用户授权；本门禁不扩大外部写入权限。

## 4. 最小机械校验

### 4.1 校验入口

- 增加一个Atom项目内的只读校验脚本，读取总账、当前计划、暂存差异和Git revision。
- 当前计划使用一个紧凑的“当前执行门”段保存`I/U/D/E`、当前步骤、最高必要验证层及revision绑定证据；它属于计划本身，不生成第二个状态文件。
- 校验脚本只验证五个阶段要求是否具备，不决定业务优先级、不修改文件、不运行测试、不读取聊天或Atom世界。
- 成功时保持安静；失败时只报告缺少的字段、证据或前置层级以及直接修复位置。
- 成功路径目标耗时不超过2秒且不输出明细；失败输出保持在1KB内。超出预算视为门禁自身缺陷，不得用扩大超时掩盖。

### 4.2 调用位置

- **开发控制测试**：验证项目规则没有从`AGENTS.md`、规格和计划约定中消失。
- **系统／全量入口**：进入较高验证层级前检查计划中同revision的前置证据。
- **提交前**：暂存产品代码或测试时检查当前计划是否同步更新；纯文档勘误走轻量检查。
- **巡守恢复**：读取校验结果和当前计划，不自行制造新状态。

校验不得拦截每条普通shell命令，也不建立可绕过现有Superpowers的万能开关。任何例外必须由当前规格明确允许并留在计划证据中，不能靠临时环境变量静默跳过。

## 5. 三类关键风险

### 5.1 质量风险

- **过度收窄**：只跑最小测试可能漏掉跨层回归。控制方式是保留真实关键旅程、系统门禁和最终全量；影响面不可靠时不得假装可收窄。
- **勾选造绿**：Agent可能只补文字而未形成事实。机械校验必须绑定Git revision、命令和结果；checkbox、提交或Agent自报均不能单独满足证据。
- **阻断探索**：未知根因需要调查。允许在当前步骤内开展有界Spike或systematic-debugging，但必须声明要关闭的不确定性，不能扩成无边界审查。
- **错误优先级**：自动公式可能压过用户决定。`I/U/D/E`用于显式表达和拆分，用户明确顺序始终优先，脚本不得自行重排。

### 5.2 Token风险

- **重复读取**：每个动作重读全部规格会放大输入。只在阶段门读取总账、当前规格和当前计划；普通命令不重复加载整套历史。
- **重复记录**：README、总账、规格和计划若复制同一状态会产生漂移。坚持单一所有权，其他文件只链接或保存各自负责的语义。
- **重复验证**：同revision复用可靠证据；全量只在最终候选运行一次，巡守无变化时不测试、不审查、不部署。
- **脚本噪声**：校验成功零详细输出；失败只给缺口和文件位置，不生成长篇报告。

### 5.3 耗时风险

- **门禁过密**：逐命令审批会拖慢工作。只在五个既有阶段节点检查；一个阶段内的RED—GREEN循环不重复走完整门禁。
- **等待空转**：Agent等待改为非阻塞协作；不能连续五分钟轮询。审查未返回时继续当前计划中不依赖该结果的工作。
- **全量过早**：真实旅程和审查未收口前禁止全量，避免代码改变后重复运行十分钟级套件。
- **脚本误报**：校验范围限定为项目开发治理文件和Git差异；错误必须给出确定修复动作，不能要求用户帮助解释内部状态。

## 6. 失败与恢复

- **缺少收件**：先补总账／规格，再回到原计划；新反馈不自动插队。
- **缺少计划字段**：在当前计划补齐，不重新创建计划或重开已批准设计。
- **越级验证**：停止高层测试，执行缺失的直接前置层；已有同revision证据可回填引用。
- **提交不同步**：补当前计划与恢复断点后再提交，不用聊天回忆替代。
- **中断恢复**：新Session从README进入总账和当前计划，首个未满足门禁即为下一动作；无需扫描完整会话。

## 7. 验收矩阵

| 场景 | 必须结果 |
|---|---|
| 用户提出新Bug但当前P0未完成 | Bug当轮入账，除非用户改序或构成必要依赖，否则不切换当前计划 |
| 当前计划缺少`I/U/D/E`或交付终态 | 实现阶段稳定拒绝并指向缺失字段 |
| 仅聚焦测试通过便启动全量 | 验证升级稳定拒绝并要求真实关键旅程／系统前置证据 |
| 同revision重复全量 | 复用已有证据，不启动第二次 |
| 全量因执行器／基础设施失败而无有效结果 | 记录外部失败后允许重跑；若存在真实测试失败则拒绝原样全量重跑 |
| 代码在全量后改变 | 候选解冻，从最小受影响链重新开始 |
| 产品代码已暂存但计划未更新 | 提交稳定拒绝，纯文档勘误不被误拦 |
| 等待Agent超时 | 不原样连续等待；继续合法本地步骤或记录真实阻塞 |
| `U3`且目标`E3` | 未部署及公共入口回读前不得关闭 |
| 无变化的每小时巡守 | 不运行测试、审查、部署或生成冗长输出 |
| 插件升级或换Session | 不依赖插件改造、私有JSONL或第二账本即可恢复 |

## 8. 完成判据

- 五个门禁进入Atom项目规则、验收规格和计划约定，但官方Superpowers插件保持只读。
- 一个小型只读校验入口覆盖阶段缺口、验证越级和提交不同步；不存在常驻进程或第二套状态存储。
- 质量证据不减少；同revision重复全量、连续Agent等待和无账本代码提交得到阻断。
- 聚焦校验、开发控制测试及模拟Git差异场景通过，且脚本成功路径保持低输出和低延迟。
- 在生产规模仓库状态下，校验成功路径不超过2秒、无明细输出；失败输出不超过1KB并给出唯一直接修复位置。
- 当前需求总账、恢复入口和实施计划能够在聊天完全缺失时给出唯一下一动作。
