# Atom 局部原子提交设计

## 目标与用户定论

- **局部闭环**：每个合法 Transform 以其实际影响的局部事实集合为一个原子；十笔独立操作完成七笔时，七笔新值可读，另外三笔继续显示各自旧值。
- **读取边界**：局部提交的持久化点之前，Explore 读取该局部的旧稳定值；持久化点之后读取新稳定值；任何读取不得组合新事实与旧兼容清单。
- **冲突边界**：只有实际影响集合相交且前置事实已变化的提交才冲突。不同槽例、不同无关子树或不同无关轴不得因共享整世界指纹而互相拒绝。
- **速度方向**：局部提交的热路径只持久化局部记录，不重复序列化整棵世界；整世界快照作为异步压实与恢复材料，不再决定单笔局部提交何时完成。

## 系统本体

- **权威事实仓**：拥有已提交的Graph四轴事实；读取只暴露完整提交边界。
- **局部提交记录**：记录一个Transform的局部前像、后像、影响闭包、关联标识与提交次序；其落盘完成是该局部的持久化点。
- **压实快照**：把已提交局部记录折叠为可快速启动的整世界基线；属于可重建恢复材料，不与局部记录争夺权威。
- **世界指纹**：表示某一已提交组合状态，用于回执、投影排序和全局观察；不再单独充当无关局部写入的冲突钥匙。
- **兼容清单**：与同一次已提交读取快照绑定；不能从事务日志另取旧清单后再读取新事实。
- **派生投影**：Graph/Web/knowledge从已提交状态异步重建；失败可恢复，不阻塞局部事实提交。

## 合同矩阵

| 生产者 | 消费者 | 输入 | 输出 | 失败 | 不变量 |
|---|---|---|---|---|---|
| World Service | Engine/Explore | 世界与请求身份 | `facts + worldFingerprint + compatibilityManifest`同源快照 | 一致性读取失败 | 不返回混搭状态 |
| Transform Engine | Commit Coordinator | 候选事实、changedPaths、轴级影响及引用闭包 | 局部补丁候选 | 影响集合不完整 | 单次Transform全部或全不提交 |
| Commit Coordinator | Local Commit Store | 局部前置指纹、补丁、回执身份 | 已落盘提交记录 | 同局部前像变化 | 无关局部变化不构成冲突 |
| Local Commit Store | Snapshot Compactor | 已提交记录序列 | 新基线与压实水位 | 压实失败 | 已提交记录仍可读取和恢复 |
| Projection Runtime | Web/CLI | 已提交世界指纹与影响集合 | 对应投影 | 发布延迟或失败 | 旧投影不能覆盖新指纹 |

## 运行模型

### 查询

- 请求开始时取得一次同源已提交快照，Engine、Agent解析与Explore共用它。
- 请求进行期间其他局部提交完成，不改变本请求已取得的视图；下一次请求读取新组合状态。
- 来源提交后需要回读时重新取得快照，不沿用来源提交前的兼容清单。

### 提交

1. Transform基于已提交快照形成候选与精确影响闭包。
2. 提交器核对影响闭包内的局部前像；无关路径的变化允许保留并合并。
3. 一条局部提交记录完成校验、追加和`fsync`后，该Transform成为已提交。
4. 内存视图原子切换到新组合状态并返回回执；后续Program、投影和压实各自继续。
5. 多路径Transform仍是一条记录、一个原子边界，不能拆成七成功三失败；“七发完成”指七个独立Transform。

### 冲突

- 同一Atom同一轴、祖先整体迁移与其后代编辑、关系端点或锁闭包相交时，前像不符则返回局部冲突。
- 不同槽例的独立数据节点在影响闭包不相交时直接合并，不要求客户CLI重放整个业务命令。
- 已有同请求标识幂等、权限重验、引用守恒和Program后续独立回执保持不变。

## 持久化与恢复

- **提交日志**：复用现有增量事务目录与local-patch能力，新增明确的已提交水位和轴级前像；不建立第二套业务账本。
- **启动恢复**：加载最近压实基线，只重放水位之后校验通过的已提交局部记录；prepared而未committed的记录不得对读取可见。
- **压实**：在提交热路径之外生成新整世界文件，校验指纹后原子替换基线并推进水位；失败只保留旧基线与日志。
- **回滚**：按原提交的逆向局部补丁执行新提交；无关后来变更保留。影响闭包已经变化时拒绝，不恢复整世界旧快照。
- **迁移**：现有整世界文件成为首个基线，既有事务与回执保持可读；切换前创建私密完整备份，生产事实不在代码部署时重放。

## 性能与可观测性

- 12k级当前世界的普通单局部提交热路径不得重新写整世界JSON；记录局部日志追加、校验、`fsync`和回执各阶段耗时。
- 初始工程目标为热态普通局部提交持久化确认不超过1秒；以真实规模副本的p50/p95和记录字节数验收，不用缓存读取时间冒充提交时间。
- 每次提交记录关联标识、影响路径数、局部记录字节数、基线水位和压实滞后；不得记录Program正文或用户内容到额外诊断出口。

## 安全与兼容

- 权限仍按Graph路径、Agent身份、lock及slot结构判定；局部化不放宽任何权限。
- `thing/situation/slot/strut`为权威轴。备份和不可变历史里的旧`detail`原样保全；非备份活跃旧Program按既定规则整体归档后四轴新建。
- `submit/$feedback`只登记线索；不进入提交器、不修改生产事实。
- 世界指纹、现有回执字段和公开错误码在迁移期保持可读；新增局部冲突细节只补充受影响路径，不暴露其他局部内容。

## 分阶段迁移

- **阶段A—一致读取**：请求取得同源事实与兼容清单，关闭`GRAPH_COMPATIBILITY_MANIFEST_REVISION_MISMATCH`竞态。
- **阶段B—局部冲突**：复用local patch，在提交时按前像重基到最新世界；先让不同槽例不冲突，重叠局部仍拒绝。
- **阶段C—局部持久化**：已提交local patch日志成为热路径，整世界写入移出提交路径并异步压实。
- **阶段D—生产切换**：真实副本迁移、崩溃恢复、精确回滚、CLI/Web旅程、性能与回退全部通过后，备份生产再受控部署。

## 验收矩阵

- **七成可见**：十个独立局部提交受控暂停三笔，读取显示七个新局部与三个旧局部，绝无半笔状态。
- **同局部冲突**：同一轴两笔并发只有一笔提交；失败方不覆盖、不静默重放。
- **不同槽例**：两槽例并发均提交，无`WORLD_REVISION_CONFLICT`，回执和历史不串线。
- **一致快照**：在读取取得清单后插入提交，旧请求返回旧自洽状态，下一请求返回新自洽状态。
- **崩溃点**：日志追加前、追加后、内存切换前、压实临时文件及替换后分别注入故障，重启后只出现完整旧值或完整新值。
- **守恒**：改名、移动、归档/恢复、Strut、Shortcut、lock、slot body、Program后续和投影排序合同全部保持。
- **回退**：关闭局部提交模式并恢复切换前基线与事务备份，旧运行时可正常只读；不得丢弃切换后的生产提交，生产回退前必须停写并导出完整新状态。
